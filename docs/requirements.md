# Team Request Tracker — MVP Requirements

## Purpose

The Team Request Tracker is a sanitized training application that demonstrates a specification-first development workflow. It helps a small fictional team record, find, prioritize, and update internal requests in one browser.

The demo uses fictional sample data only. It does not connect to ICJIA, agency, production, or third-party systems.

## Users and goals

The primary user is a team coordinator who needs to:

- see the current request workload at a glance;
- create and edit requests without leaving the page;
- find requests by title or description;
- narrow the list using multiple filters; and
- retain changes after refreshing the browser.

## Data model

Each request contains:

| Field | Rules |
| --- | --- |
| ID | Unique, generated by the application |
| Title | Required; 3–80 trimmed characters |
| Description | Optional; at most 500 trimmed characters |
| Category | Required; `Data`, `Research`, `Technology`, or `Operations` |
| Priority | Required; `Low`, `Medium`, or `High` |
| Status | Required; `New`, `In progress`, `Blocked`, or `Complete` |
| Due date | Optional valid calendar date; today or later when created or changed |
| Created at | Generated ISO timestamp, retained during edits |
| Updated at | Generated ISO timestamp, refreshed during edits |

## Functional requirements

### Request list

- On first use, show fictional sample requests spanning multiple categories, priorities, and statuses.
- Show request title, description, category, priority, status, and due date.
- Visually distinguish priority and status without relying on color alone.
- Show the number of visible requests and total requests.
- Show an informative empty state when no requests exist.
- Show a distinct no-results state when requests exist but filters match none.

### Create and edit

- A clearly labeled control opens a form for a new request.
- Selecting Edit on a request opens the same form populated with current values.
- Saving a valid form updates the list immediately and closes the form.
- Cancel closes the form without changing data.
- Validation appears next to the relevant field and the first invalid field receives focus.
- Required values, length limits, allowed enum values, and due-date rules are enforced.

### Search and filters

- Search is case-insensitive and matches title or description.
- Category, priority, and status filters can be used individually or in combination with search.
- All active criteria use AND logic.
- A Clear all control resets search and all filters.
- Filter controls have accessible labels and expose their current values.

### Persistence

- Requests are stored in browser `localStorage` after every successful create or edit.
- Saved requests are restored on subsequent loads.
- Missing, malformed, or structurally invalid stored data falls back safely to fictional sample data.

### Responsive and accessible interaction

- The application supports phone, tablet, and desktop widths without horizontal page scrolling.
- On smaller screens, controls and request cards stack in a readable order.
- All actions and form controls are operable by keyboard.
- Focus indicators are visible.
- The modal form traps focus, closes with Escape, and restores focus to its opener.
- Status messages and validation feedback are exposed to assistive technology.
- Text and controls meet WCAG 2.1 AA contrast targets.

## Acceptance scenarios

1. On a fresh browser profile, fictional sample requests appear.
2. A user creates a valid high-priority Technology request; it appears and survives reload.
3. A user edits its status to Complete; the card and persisted data reflect the change.
4. Search plus category, priority, and status filters return only requests matching every criterion.
5. Clear all restores the unfiltered list.
6. A search with no matches shows a no-results explanation and Clear all action.
7. Clearing browser data and removing all requests results in the empty-workspace state.
8. Blank or too-short titles cannot be saved and show actionable errors.
9. An impossible, malformed, or past due date cannot be saved when newly entered or changed.
10. Keyboard users can open, complete, cancel, and dismiss the form with predictable focus.
11. Unit tests, a production build, and browser tests pass.

## Explicitly out of scope

- Authentication, authorization, user accounts, or roles
- Cloud, server, database, or cross-device storage
- Email, SMS, push, calendar, or other notifications
- Production deployment, hosting, monitoring, analytics, or telemetry
- Agency data, agency branding, confidential information, or live system integrations
- Attachments, comments, request deletion, bulk edits, audit history, and real-time collaboration

## Definition of done

- Requirements and architecture decisions are committed before implementation.
- The application implements the stated MVP with React, TypeScript, Vite, and plain CSS.
- Automated unit/component and Playwright scenarios cover the primary flows and regression cases.
- UAT documents preserve observed results, including defects and their corrections.
- The feature branch is pushed for review without opening or merging a pull request or creating a release tag.
